# EVS + VCF 9 Automation

End-to-end automation for standing up an Amazon EVS environment and bringing up
VMware Cloud Foundation 9.0.x on top of it. The flow is split into three
sequential phases, each with its own README that is the source of truth for
that phase:

1. **Phase 1** — Terraform that provisions the AWS networking and supporting
   infrastructure (VPC, subnets, route tables, Route 53, Route Server, optional
   public HCX, Transit Gateway, Windows jumpbox).
   See [`Phase_1_Base_Infrastructure/README.md`](Phase_1_Base_Infrastructure/README.md).
2. **Phase 2** — Python CLI that calls the EVS API to create the environment,
   add ESXi hosts, attach the post-deployment EBS volume, and generate the
   inputs for Phase 3 directly from Phase 1 state. See
   [`Phase_2_evs_env/README.md`](Phase_2_evs_env/README.md).
3. **Phase 3** — Python CLI that drives the VCF Installer (`POST /v1/sddcs`),
   then NSX Manager and vCenter to deploy the NSX edge cluster. See
   [`Phase_3_VCF9/README.md`](Phase_3_VCF9/README.md).

This top-level README is an orientation. For full action lists, flags, and
troubleshooting, jump into the per-phase README linked above.

## Prerequisites

- An AWS account with permissions matching
  [`Phase_1_Base_Infrastructure/iam_policy.json`](Phase_1_Base_Infrastructure/iam_policy.json).
  Phase 3 additionally needs `secretsmanager:CreateSecret` and
  `secretsmanager:PutSecretValue` for the installer-password stash on first
  prompt.
- AWS credentials configured (via `AWS_PROFILE`, environment variables, or an
  assumed role).
- Terraform 1.5+.
- Python 3.10+.
- A Broadcom Download Token. Generate it in the Broadcom Support Portal →
  My Dashboard → Quick Links → Generate Download Token. Used by Phase 3 to
  fetch VCF 9.0.x binaries.
- Service-linked roles for Route Server, EVS, and Transit Gateway. AWS
  auto-creates these on first use.

## Configuration Files

You must create these from the templates before running:

| Source (in repo)                                              | Target (you create)                                  | Used by                          |
|---------------------------------------------------------------|------------------------------------------------------|----------------------------------|
| `Phase_1_Base_Infrastructure/terraform.tfvars.example`        | `Phase_1_Base_Infrastructure/terraform.tfvars`       | Phase 1 Terraform                |
| `Phase_2_evs_env/python/config.example.json`                  | `Phase_2_evs_env/python/config.json`                 | Phase 2 Python (all actions)     |

Files generated automatically (do not hand-edit):

- `Phase_2_evs_env/python/state.json` — Phase 2 handoff to its trailing
  AWS actions (route table ID, target instance ID, AZ, VLAN subnet IDs).
  Written by `post-evs-sync-config`.
- `Phase_3_VCF9/bringup_spec.json` — VCF bringup spec. Written by
  `pre-evs-sync-config` with `__SECRET:` placeholders, regenerated by
  `post-evs-sync-config` with the real environment-ID-derived names.
- `Phase_3_VCF9/edge_cluster_spec.json` — NSX edge cluster spec. Same
  two-pass write pattern.

Phase 2 also patches `config.json` itself in place (e.g. writes back the
`environmentId` after `create-environment`).

## End-to-End Flow

> **Windows note:** Where only `bash` examples are shown for AWS CLI or
> Terraform commands, the only change needed on Windows PowerShell is the
> line-continuation character: replace `\` with `` ` `` (backtick), or write
> the command on a single line. Platform-specific sections (venv setup,
> env vars, scripted loops) show both Linux/macOS and Windows variants.

### Phase 1: Base Infrastructure

```bash
cd Phase_1_Base_Infrastructure
cp terraform.tfvars.example terraform.tfvars
```

> **Edit `terraform.tfvars` now.** You must set `region`, `availability_zone`,
> and `fqdn` before running `terraform apply`. The example file ships with
> placeholder values (`us-east-1` / `us-east-1a` / `my.fqdn.evs`) — applying
> without editing deploys to the wrong region under the wrong DNS name.

**Linux / macOS:**
```bash
export AWS_PROFILE=your-profile-name
terraform init
terraform plan
terraform apply
```

**Windows (PowerShell):**
```powershell
$env:AWS_PROFILE = "your-profile-name"
terraform init
terraform plan
terraform apply
```

#### Optional toggles

| Toggle | Default | Description |
|--------|---------|-------------|
| `create_tgw` | `false` | Creates a Transit Gateway + VPC attachment for on-premises connectivity |
| `create_jumpbox` | `true`  | Creates a Windows EC2 jumpbox for RDP access to the ESXi management network. **Required for Phase 3 manual pre-work.** |
| `enable_public_hcx` | `false` | Provisions a public /28 CIDR, EIP, and Network ACL for HCX public connectivity |

Hostname overrides and other optional variables are listed in the
[Phase 1 README](Phase_1_Base_Infrastructure/README.md#optional-components).

#### Validate Phase 1

After `terraform apply` succeeds, confirm key outputs:

```bash
terraform output vpc_id
terraform output service_access_subnet_id
terraform output jumpbox_public_ip        # if create_jumpbox = true
terraform output hcx_eip_allocation_id    # if enable_public_hcx = true
```

All values should be non-null. If any are empty, that component did not
provision — check the Terraform error output before continuing.

Phase 2 reads Phase 1's outputs directly from
`Phase_1_Base_Infrastructure/terraform.tfstate` via the
`pre-evs-sync-config` action. You do not have to copy outputs by hand.

#### Optional: Public HCX

Set `enable_public_hcx = true` in `terraform.tfvars` to provision the
IPAM-backed public `/28`, the EIP allocated from that pool, and the HCX
Network ACL alongside the rest of the underlay. After `terraform apply`,
sanity-check that the three new outputs are non-null before continuing —
if any are null, public HCX did not provision and Phase 2 will silently
fall through to the private flow:

```bash
terraform output hcx_public_cidr
terraform output hcx_network_acl_id
terraform output hcx_eip_allocation_id
```

Phase 2's `pre-evs-sync-config` populates `initialVlans.hcx.cidr`,
`isHcxPublic`, `hcxNetworkAclId`, and `hcxEipAllocationId` from these
outputs. The `associate-hcx-eip` action (run between `create-environment`
and `create-hosts`) then attaches the EIP to the EVS HCX VLAN. Phase 3 is
unchanged.

The HCX Network ACL ships with no ingress or egress rules, so HCX
traffic is dropped at the subnet boundary by default. Add explicit
allow rules for the operator (or partner) CIDR before HCX is reachable
— the rule numbers are operator's choice (any unique, ordered values
work) and the port set should match your HCX deployment shape (HCX
Manager UI / REST, tunnel, L2C/extension, etc.).

Use `aws ec2 create-network-acl-entry` once per ingress rule and once
for egress:

```bash
# Inbound: one call per protocol/port combination you need to allow
# from your operator CIDR.
aws ec2 create-network-acl-entry \
  --network-acl-id <hcx_network_acl_id_from_terraform_output> \
  --rule-number <unique-rule-number> --protocol <tcp|udp> \
  --port-range From=<port>,To=<port> \
  --rule-action allow --cidr-block <your-mgmt-cidr> --ingress \
  --region <region> --profile <your-profile>

# Outbound: one call to allow return traffic. Tighten if your security
# posture requires it.
aws ec2 create-network-acl-entry \
  --network-acl-id <hcx_network_acl_id_from_terraform_output> \
  --rule-number <unique-rule-number> --protocol -1 \
  --rule-action allow --cidr-block 0.0.0.0/0 --egress \
  --region <region> --profile <your-profile>
```

Without these rules the EVS environment will come up cleanly but every
inbound HCX flow is silently denied at the NACL.

> **Switching to private HCX:** If you disable `enable_public_hcx` after a
> prior public deployment, re-run `pre-evs-sync-config` — it removes the
> public HCX fields that the EVS API rejects in private mode.

#### Optional: Jumpbox

The jumpbox security group is created with no RDP ingress. After
`terraform apply`, add a TCP 3389 rule from your IP via the AWS Console.
Then retrieve the auto-generated key pair and Windows administrator
password — see the
[Phase 1 README jumpbox section](Phase_1_Base_Infrastructure/README.md#accessing-the-jumpbox).

### Phase 2: EVS Environment

**Linux / macOS:**
```bash
cd Phase_2_evs_env/python
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp config.example.json config.json   # then edit
```

**Windows (PowerShell):**
```powershell
cd Phase_2_evs_env\python
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

Copy-Item config.example.json config.json   # then edit
```

In `config.example.json` the fields most operators need to set
before `pre-evs-sync-config` are `environmentName` and
`vcfInstallerProductVersion` (e.g., `"9.0.2.0"` or `"9.1.0.0"` —
must match the OVA you deploy). Everything else (`region`, `vpcId`,
subnet IDs, security groups, VLAN CIDRs, DNS servers, hostnames,
public-HCX fields) is patched in from `terraform.tfstate`.

> **Recommended:** Use the one-shot `deploy-environment` command to run
> all 7 steps end-to-end:
>
> ```bash
> python -m src.main deploy-environment \
>   --config config.json \
>   --tfstate ../../Phase_1_Base_Infrastructure/terraform.tfstate \
>   --instance-type i4i.metal
> ```
>
> This handles environment creation, host provisioning (with polling),
> post-sync, VLAN association, HCX EIP, and EBS volume in one call.
> If you prefer to run steps individually (e.g., for debugging), see
> the breakdown below.

The 7-step pipeline is:

1. `pre-evs-sync-config` — read Phase 1 tfstate, patch `config.json`,
   write placeholder Phase 3 specs. No AWS calls.
2. `create-environment` — call EVS `CreateEnvironment`; writes
   `environmentId` back into `config.json`.
3. `associate-hcx-eip` — public HCX only.
4. `create-hosts` — add ESXi hosts to the environment.
5. `post-evs-sync-config` — find the EVS-tagged EC2 instance, list VLAN
   subnets, generate VCF appliance passwords into Secrets Manager,
   regenerate Phase 3 specs with real env-ID-derived names, write
   `state.json`.
6. `associate-vlan-subnets` — re-associate every EVS VLAN subnet with
   Phase 1's service-access route table.
7. `create-and-attach-ebs` — create the 256 GB gp3 volume that hosts the
   VCF Installer VMFS, attach to the host that will run the OVA.

`create-environment-and-hosts` chains steps 2 + 4 (with a `CREATED`
poll between). `deploy-environment` is the one-shot wrapper that runs
all 7 steps end-to-end.

Each individual action also accepts `--dry-run`. Full flag table and
per-action notes live in the
[Phase 2 README](Phase_2_evs_env/README.md#python-actions).

### Manual ESXi Pre-Work and VCF Installer OVA Deploy (REQUIRED before Phase 3)

> **You must complete these manual steps before running Phase 3.**
> Phase 3 will fail without them. These steps require network access to
> the ESXi management subnet — use the jumpbox (RDP).
> If you didn't enable `create_jumpbox = true` in Phase 1, go back and
> set it, then `terraform apply` again.
>
> **Connect to the jumpbox:** See
> [Phase 1 README — Accessing the Jumpbox](Phase_1_Base_Infrastructure/README.md#accessing-the-jumpbox)
> for IP retrieval, SSH key download, password decryption, and RDP
> connection steps.

Between Phase 2 and Phase 3 you have to:

1. **VLAN 20 tagging** — on the host with the EBS volume:
   - Open the ESXi web UI (`https://<host-IP>`) and log in as `root`
   - Navigate: **Networking** → **Port groups** tab
   - Click **VM Network** → **Edit settings**
   - Set **VLAN ID** to `20` → **Save**

2. **Create VMFS datastore** — same host:
   - Navigate: **Storage** (left menu)
   - Click **New Datastore**
   - Select **Create new VMFS datastore** → Next
   - Name it `VCF-Installer-VMFS`
   - Select the **256 GB NVMe device** (the EBS volume)
   - Use **VMFS 6**, full disk allocation → Finish

3. **Deploy the VCF Installer OVA** onto the VMFS datastore:
   - In the ESXi web UI (same host as step 2), click **Actions** →
     **Deploy OVF Template**
   - Select the locally downloaded OVA file (download from Broadcom
     Support Portal)
   - Target datastore: `VCF-Installer-VMFS`
   - Set management IP to the SDDC Manager IP from your DNS plan
     (`sddcm.<fqdn>` — default `<cidr_prefix>60.12`, e.g. `10.0.60.12`)
   - Set the `admin@local` password (you'll need it for Phase 3)

To find which ESXi host owns the EBS volume (and therefore where the
local VMFS datastore + OVA must land), map the volume to its EC2
instance ID:

**Linux / macOS:**
```bash
aws ec2 describe-volumes \
  --filters "Name=tag:ManagedBy,Values=phase2-automation" \
            "Name=tag:EnvironmentId,Values=<environment_id_from_config_json>" \
  --query 'Volumes[0].Attachments[0].InstanceId' --output text \
  --region <region> --profile <your-profile>
```

**Windows (PowerShell):**
```powershell
aws ec2 describe-volumes `
  --filters "Name=tag:ManagedBy,Values=phase2-automation" `
            "Name=tag:EnvironmentId,Values=<environment_id_from_config_json>" `
  --query 'Volumes[0].Attachments[0].InstanceId' --output text `
  --region <region> --profile <your-profile>
```

Then open the instance in the EC2 console — its Name tag is the ESXi
hostname (`esxi01` / `esxi02` / `esxi03`).

To log into the ESXi host UI you need the per-host root password. EVS
manages those secrets under `evs!<env_id>_<host>` (bang form). Retrieve:

**Linux / macOS:**
```bash
ENV_ID=$(python3 -c "import json; print(json.load(open('Phase_2_evs_env/python/config.json'))['environmentId'])")
aws secretsmanager get-secret-value \
  --secret-id "evs!${ENV_ID}_esxi01" \
  --profile <your-profile> --query SecretString --output text
```

**Windows (PowerShell):**
```powershell
$ENV_ID = (Get-Content Phase_2_evs_env\python\config.json | ConvertFrom-Json).environmentId
aws secretsmanager get-secret-value `
  --secret-id "evs!${ENV_ID}_esxi01" `
  --profile <your-profile> --query SecretString --output text
```

### Phase 3: VCF Bringup + NSX Edge Cluster

> **Network access required.** Phase 3 scripts talk directly to the VCF
> Installer, NSX Manager, and vCenter on the management subnet. Run them
> from the **Windows jumpbox** (via RDP) which has direct access to the
> ESXi management network.

**Windows (PowerShell) — run from the jumpbox:**
```powershell
cd Phase_3_VCF9\python
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

$env:VCF_INSTALLER_PASSWORD = [Net.NetworkCredential]::new('', (Read-Host -AsSecureString -Prompt 'VCF_INSTALLER_PASSWORD')).Password
$env:VCF_DEPOT_TOKEN = [Net.NetworkCredential]::new('', (Read-Host -AsSecureString -Prompt 'VCF_DEPOT_TOKEN')).Password

python -m src.main deploy-vcf-and-edge --installer-host sddcm.<fqdn> --target-version 9.0.2 --nsx-manager-host nsx.<fqdn> --vcenter-host vc.<fqdn> --aws-profile <your-profile>
```

**Linux / macOS:**
```bash
cd Phase_3_VCF9/python
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

read -rs VCF_INSTALLER_PASSWORD ; export VCF_INSTALLER_PASSWORD
read -rs VCF_DEPOT_TOKEN        ; export VCF_DEPOT_TOKEN

python -m src.main deploy-vcf-and-edge \
  --installer-host sddcm.<fqdn> \
  --target-version 9.0.2 \
  --nsx-manager-host nsx.<fqdn> \
  --vcenter-host vc.<fqdn> \
  --aws-profile <your-profile>
```

`deploy-vcf-and-edge` is the **one-click SDDC + NSX edge cluster
deployment**: it chains `prepare-depot` (token + sync + binary
download) → `start-bringup --wait` → installer datastore cleanup →
EBS volume destroy → NSX edge cluster (7 stages) → EVS connector
registration in one call. Total runtime ~3-5 hours, dominated by
bringup.

Each step is also runnable individually for partial reruns or
inspection. The full action catalog (24 actions across 7 buckets:
bringup, depot, NSX/vCenter ping, vCenter cleanup, AWS cleanup, edge
cluster, pipeline) and complete CLI flag reference live in the
[Phase 3 README](Phase_3_VCF9/README.md).

NSX Manager and vCenter SSO passwords resolve from AWS Secrets Manager
(`evs-<env>_nsxAdmin` and `evs-<env>_vcenterSso`) at runtime. The VCF
Installer `admin@local` password and the Broadcom depot token come
from CLI flag → env var → Secrets Manager → prompt. After a fresh
first-time prompt the installer password is stashed back into Secrets
Manager so subsequent runs are prompt-free.

## Cleanup / Teardown

Tear down in reverse order. There is currently no automation for
deleting the EVS environment itself or the Secrets Manager secrets
Phase 2 created — both are manual today.

**Linux / macOS:**
```bash
# Delete the EVS environment (and the ESXi hosts it owns).
ENV_ID=$(python3 -c "import json; print(json.load(open('Phase_2_evs_env/python/config.json'))['environmentId'])")
REGION=$(python3 -c "import json; print(json.load(open('Phase_2_evs_env/python/config.json'))['region'])")
aws evs delete-environment --environment-id "$ENV_ID" \
  --region "$REGION" --profile <your-profile>
```

**Windows (PowerShell):**
```powershell
# Delete the EVS environment (and the ESXi hosts it owns).
$config = Get-Content Phase_2_evs_env\python\config.json | ConvertFrom-Json
$ENV_ID = $config.environmentId
$REGION = $config.region
aws evs delete-environment --environment-id $ENV_ID `
  --region $REGION --profile <your-profile>
```

Wait for the environment to fully tear down (this also removes the
ESXi hosts and the VCF Installer / SDDC Manager VM running on them),
then:

**Linux / macOS:**
```bash
# Optional — delete the VCF appliance secrets Phase 2 created.
# The ESXi root secrets (evs!<env>_<host>) are deleted by EVS when
# the environment is deleted; the appliance secrets (evs-<env>_*)
# are not.
aws secretsmanager list-secrets \
  --filters "Key=name,Values=evs-${ENV_ID}_" \
  --region "$REGION" --profile <your-profile> \
  --query 'SecretList[].Name' --output text \
  | xargs -n1 -I{} aws secretsmanager delete-secret \
      --secret-id {} --force-delete-without-recovery \
      --region "$REGION" --profile <your-profile>

# Phase 1 Terraform (VPC and supporting infra; jumpbox / TGW / public HCX
# if enabled).
cd Phase_1_Base_Infrastructure
terraform destroy
```

**Windows (PowerShell):**
```powershell
# Optional — delete the VCF appliance secrets Phase 2 created.
(aws secretsmanager list-secrets `
  --filters "Key=name,Values=evs-${ENV_ID}_" `
  --region $REGION --profile <your-profile> `
  --query 'SecretList[].Name' --output text) -split "`t" | ForEach-Object {
  aws secretsmanager delete-secret --secret-id $_ --force-delete-without-recovery `
    --region $REGION --profile <your-profile>
}

# Phase 1 Terraform
cd Phase_1_Base_Infrastructure
terraform destroy
```

If a Phase 3 run failed partway through, every action is idempotent —
fix the underlying issue and re-run `deploy-vcf-and-edge`. Already-done
substeps (depot bundles downloaded, bringup completed, EBS gone) are
fast-forwarded and the chain resumes at the broken step.

## Operational Notes

- `Phase_3_VCF9/bringup_spec.json` and `edge_cluster_spec.json` are
  regenerated idempotently by the Phase 2 sync actions. Do not
  hand-edit them — re-run `pre-evs-sync-config` /
  `post-evs-sync-config` instead.
- VCF appliance passwords are managed via AWS Secrets Manager.
  `post-evs-sync-config` generates and stores them as
  `evs-<env_id>_<role>` secrets. The on-disk spec files carry
  `__SECRET:<role>__` placeholders that Phase 3 resolves at runtime —
  no plaintext passwords touch disk.
- ESXi root passwords are managed by the EVS service and live under
  `evs!<env_id>_<host>` (bang form). Phase 3 resolves them via
  `__SECRET:esxi:<host>__` placeholders the same way.
- After Phase 1, the jumpbox security group has no RDP ingress by
  default — you must add a rule from your IP before connecting.

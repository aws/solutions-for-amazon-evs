# Phase 2 - EVS Environment Deployment

Python automation for the EVS API plus the post-EVS infrastructure
(VLAN route table associations, EBS volume attach for the VCF Installer
VMFS). Earlier versions used Terraform for the post-EVS bits; that
layer was ported to Python to consolidate the codebase.

## Directory Structure

```
Phase_2_evs_env/
└── python/                # Python CLI for EVS API + post-EVS AWS infra
    ├── src/               # Source code
    ├── config.json        # Deployment config (gitignored)
    ├── config.example.json
    ├── state.json         # Auto-generated by post-evs-sync-config (gitignored)
    └── requirements.txt
```

## Prerequisites

- Python 3.10+
- AWS credentials configured in `~/.aws/credentials`
- Phase 1 infrastructure deployed
- `python/config.json` populated (start from `config.example.json` — license keys are not required; bringup uses `deployWithoutLicenseKeys: true`)

## Python Actions

> **Recommended:** Use `deploy-environment` to run all steps in one
> command (see [Deploy Environment](#deploy-environment-full-pipeline-one-shot)).
> The individual steps below are available for debugging or partial
> re-runs.

> **Before running:** Verify `vcfInstallerProductVersion` in `config.json`
> matches the VCF Installer OVA you plan to deploy (e.g., `"9.0.2.0"` for
> VCF 9.0.2, `"9.1.0.0"` for VCF 9.1). This controls the bringup spec
> version field and determines which version-specific components are included.

### Deploy Environment (full pipeline, one-shot)

Chains every step into a single command. Equivalent to running:

1. `pre-evs-sync-config`
2. `create-environment-and-hosts` (which already chains create-environment → wait for `CREATED` → create-hosts)
3. Wait for every host to reach `CREATED` (host realization is 20-40 min)
4. `post-evs-sync-config`
5. `associate-vlan-subnets`
6. `associate-hcx-eip`
7. `create-and-attach-ebs`

Total runtime: ~30-50 minutes, dominated by step 3 (host realization).
The step 3 wait has a 90-minute hard ceiling so a stuck environment
won't hang the CLI forever; fatal host states (`FAILED`, `CREATE_FAILED`)
abort the chain immediately.

Steps 5–7 read state in-memory from step 4's output rather than
re-reading `state.json` from disk.

```bash
python -m src.main deploy-environment \
  --profile <your-profile> \
  --config config.json \
  --tfstate ../../Phase_1_Base_Infrastructure/terraform.tfstate \
  --instance-type i4i.metal
```

For operators who want to inspect state between steps (verify env shape
before submitting host creates, examine VLAN subnet IDs before generating
Phase 3 specs, etc.), the individual actions below remain available.

---

### 1. Pre-EVS Sync Config

Reads the Phase 1 Terraform state and updates `config.json` with region, VPC ID, subnet ID, security group, VLAN CIDRs, DNS servers, VCF + ESXi hostnames, and the Route Server endpoint IPs (used later by Phase 3 for BGP). Also writes two initial spec files to `Phase_3_VCF9/` with env-ID placeholders that `post-evs-sync-config` fills in later:

- `bringup_spec.json` — the VCF bringup spec. Built as a typed
  `vmware.vcf_installer.model_client.SddcSpec` object and serialized via
  the SDK's own converter (so the JSON on disk is exactly what Phase 3
  will POST). The VCF target version (9.0 vs 9.1) is derived automatically
  from `vcfInstallerProductVersion` to control which version-specific extras
  get included.
- `edge_cluster_spec.json` — internal Phase 2 ↔ Phase 3 contract for the
  NSX edge cluster deployment. Stays a plain dict because the edge
  workflow is our own staging, not a single VMware API shape.

No AWS credentials needed for this action.

```bash
# Dry run
python -m src.main pre-evs-sync-config \
  --config config.json \
  --tfstate ../../Phase_1_Base_Infrastructure/terraform.tfstate \
  --dry-run

# Apply
python -m src.main pre-evs-sync-config \
  --config config.json \
  --tfstate ../../Phase_1_Base_Infrastructure/terraform.tfstate
```

> **Verify:** After running, confirm that `fqdn` in `config.json` matches
> your Route 53 hosted zone domain. All VCF component hostnames are derived
> from this value — a mismatch causes DNS resolution failures during bringup.

> **Switching between public and private HCX:** If you previously deployed
> with `enable_public_hcx = true` and now switch to `false`, re-run
> `pre-evs-sync-config` — it removes the stale public HCX fields
> (`isHcxPublic`, `hcxNetworkAclId`, `hcxEipAllocationId`) that the EVS
> API rejects in private mode.

### 3. Create Hosts

Adds hosts to an existing EVS environment. The environment
must already be in `CREATED` state (`deploy-environment` handles this
wait automatically; if running individually, confirm with
`aws evs get-environment --environment-id <id>` first).

**Required parameters:** `--instance-type` must be specified

```bash
# Dry run
python -m src.main create-hosts \
  --profile <your-profile> \
  --config config.json \
  --instance-type i4i.metal \
  --dry-run

# Deploy
python -m src.main create-hosts \
  --profile <your-profile> \
  --config config.json \
  --instance-type i4i.metal
```

> **ESXi version:** Automatically resolved from the EVS `get-versions`
> API based on `vcfInstallerProductVersion` and `--instance-type`. To
> override, set `esxVersion` in config.json to an exact build string
> (e.g. `"ESXi-9.1.0.0100.25433460"`).

### 3b. Create Environment + Hosts (one-shot)

Chains `create-environment` → wait for the environment to reach `CREATED`
→ `create-hosts` in a single command. Equivalent to running steps 2 and 3
back-to-back with operator-driven polling in between, but without the
manual wait. Useful when you don't need to inspect anything between
steps.

```bash
python -m src.main create-environment-and-hosts \
  --profile <your-profile> \
  --config config.json \
  --instance-type i4i.metal
```

The polling step calls `GetEnvironment` every 60 seconds and exits the
wait when the environment reaches `CREATED` (typically 5-10 minutes).
A 90-minute total budget bounds the wait so a stuck environment doesn't
hang the CLI forever. If the environment hits a fatal state
(`FAILED`, `CREATE_FAILED`), the chain aborts before submitting host
creates.

### 4. Post-EVS Sync Config

Looks up the first EC2 instance tagged `DoNotDelete-EVS-[<environmentId>]*`, queries the EVS API for the environment's VLAN subnets, and writes:

- Phase 2 state (`state.json` in `Phase_2_evs_env/python/`) — region, AZ, instance ID for the EBS attach, service access route table ID, and every EVS VLAN subnet ID for route table association. Consumed by `associate-vlan-subnets` and `create-and-attach-ebs` (or by the chained `deploy-environment` directly in-memory).
- Phase 3 bringup spec (`bringup_spec.json` in `Phase_3_VCF9/`) — the full
  typed `SddcSpec` including env-ID-derived cluster/DC/DVS names and the
  EVS instance type's matching `clusterEvcMode`
- Phase 3 edge cluster spec (`edge_cluster_spec.json` in `Phase_3_VCF9/`) —
  finalized with env-ID-derived T0/T1/edge-cluster/pool names

All three files are written every time; output paths are fixed by the Phase layout.

The Phase 3 specs are created with placeholder names during `pre-evs-sync-config`, and finalized here with the actual environment ID.

```bash
# Dry run
python -m src.main post-evs-sync-config \
  --profile <your-profile> \
  --config config.json \
  --dry-run

# Apply
python -m src.main post-evs-sync-config \
  --profile <your-profile> \
  --config config.json
```

> **Note**: `post-evs-sync-config` no longer caches anything back into
> `config.json` — ESXi root passwords are read from Secrets Manager at
> Phase 3 runtime via the `__SECRET:esxi:<host>__` placeholders the
> bringup spec carries.

> **VCF appliance secrets**: `post-evs-sync-config` also provisions
> per-role VCF appliance passwords (vCenter root + SSO, NSX
> root/admin/audit, SDDC Manager root/ssh/local, VCF Operations
> admin/master/collector, edge appliance, plus 9.0-only fleet manager
> root + admin) as Secrets Manager secrets named
> `evs-<env_id>_<role>`. Generation matches EVS's own
> `generateComplexVcfPassword` (18 characters: 17 random consonants/digits
> + trailing `!`, no vowels, no punctuation). The action is idempotent —
> existing secrets are left alone. Rotate by deleting the secret in AWS
> and re-running. The HA-only operations data + replica passwords are
> only generated when `simpleDeployment: false`; the fleet manager
> passwords only when `vcfInstallerProductVersion` starts with `"9.0"`. Phase 3 fetches these
> at runtime via the placeholders Phase 2 writes into
> `bringup_spec.json` and `edge_cluster_spec.json`.

### 5. Associate VLAN Subnets

Associates every EVS-created VLAN subnet with the service-access route
table from Phase 1. Replaces the old Phase 2
`vlan_route_associations` Terraform module.

Idempotent: subnets already associated are skipped. Tolerates the brief
window after EVS reports a subnet `CREATED` but AWS-side propagation
hasn't surfaced it to `DescribeRouteTables` yet — retries with
exponential backoff (2 → 4 → 8 → 16 → 32 sec) on
`InvalidSubnetID.NotFound` and throttling errors before giving up.
After the loop, re-describes the route table and verifies every
requested subnet appears.

Reads `state.json` for the route table ID and subnet IDs (written by
`post-evs-sync-config`).

```bash
python -m src.main associate-vlan-subnets \
  --profile <your-profile> \
  --config config.json
```

### 6. Create + Attach EBS Volume

Creates the 256 GB encrypted gp3 EBS volume that hosts the VCF
Installer VMFS, and attaches it at `/dev/sdf` to the EVS host
identified by `post-evs-sync-config`. Replaces the old Phase 2
`ebs_volume` Terraform module.

Idempotent: looks up an existing volume tagged for this env first
(`ManagedBy=phase2-automation` + `EnvironmentId=<env>`). If found,
skips create. If already attached at the requested location, skips
attach. If attached elsewhere, refuses to act.

Reads `state.json` for the AZ and target instance ID.

```bash
python -m src.main create-and-attach-ebs \
  --profile <your-profile> \
  --config config.json
```

## VCF Appliance Secrets

The `post-evs-sync-config` action (and `deploy-environment`, which calls it) automatically provisions complex passwords for every VCF appliance role and stores them in AWS Secrets Manager. Phase 3 fetches these at runtime via `__SECRET:<role>__` placeholders embedded in `bringup_spec.json` and `edge_cluster_spec.json` — no passwords touch disk.

### Secret naming

- **Appliance secrets:** `evs-<environment-id>_<role>`
- **ESXi secrets (created by EVS, not this tool):** `evs!<environment-id>_<hostname>`

### Roles provisioned

| Role | Username | Secret Name | When Created |
|------|----------|-------------|--------------|
| `vcenterRoot` | `root` | `evs-<env>_vcenterRoot` | Always |
| `vcenterSso` | `administrator@vsphere.local` | `evs-<env>_vcenterSso` | Always |
| `nsxRoot` | `root` | `evs-<env>_nsxRoot` | Always |
| `nsxAdmin` | `admin` | `evs-<env>_nsxAdmin` | Always |
| `nsxAudit` | `audit` | `evs-<env>_nsxAudit` | Always |
| `sddcManagerRoot` | `root` | `evs-<env>_sddcManagerRoot` | Always |
| `sddcManagerSsh` | `vcf` | `evs-<env>_sddcManagerSsh` | Always |
| `sddcManagerLocal` | `admin@local` | `evs-<env>_sddcManagerLocal` | Always |
| `operationsAdmin` | `admin` | `evs-<env>_operationsAdmin` | Always |
| `operationsMaster` | `admin` | `evs-<env>_operationsMaster` | Always |
| `operationsCollector` | `admin` | `evs-<env>_operationsCollector` | Always |
| `edgeAppliance` | `admin` | `evs-<env>_edgeAppliance` | Always |
| `operationsData` | `admin` | `evs-<env>_operationsData` | HA only (`simpleDeployment: false`) |
| `operationsReplica` | `admin` | `evs-<env>_operationsReplica` | HA only (`simpleDeployment: false`) |
| `fleetManagerRoot` | `root` | `evs-<env>_fleetManagerRoot` | VCF 9.0 only |
| `fleetManagerAdmin` | `admin` | `evs-<env>_fleetManagerAdmin` | VCF 9.0 only |

### Password format

Generated passwords match EVS's own `generateComplexVcfPassword`:
- 20 characters total
- At least 4 character classes (uppercase, lowercase, digit, special)
- At least 4 unique characters
- No vowels, no consecutive sequences (e.g. `abc`, `321`)
- Validated against the strictest VCF appliance constraints (SDDC Manager min 15, vCenter max 20)

### Secret storage format

Each secret is stored as JSON:

```json
{"username": "<role-username>", "password": "<generated-password>"}
```

Tagged with `EvsAccess: True` so EVS service can access them.

### Listing secrets for an environment

**Linux / macOS:**
```bash
aws secretsmanager list-secrets \
  --filters "Key=name,Values=evs-<environment-id>" \
  --query 'SecretList[].Name' --output table --region <region>
```

**Windows (PowerShell):**
```powershell
aws secretsmanager list-secrets `
  --filters "Key=name,Values=evs-<environment-id>" `
  --query 'SecretList[].Name' --output table --region <region>
```

### Retrieving a specific password

**Linux / macOS:**
```bash
aws secretsmanager get-secret-value \
  --secret-id "evs-<environment-id>_vcenterSso" \
  --region <region> \
  --query 'SecretString' --output text | python3 -c "import sys,json; print(json.load(sys.stdin)['password'])"
```

**Windows (PowerShell):**
```powershell
(aws secretsmanager get-secret-value `
  --secret-id "evs-<environment-id>_vcenterSso" `
  --region <region> `
  --query 'SecretString' --output text | ConvertFrom-Json).password
```

### Idempotency and rotation

- **Idempotent:** If a secret already exists, it is left unchanged. Re-running `post-evs-sync-config` does not overwrite existing passwords.
- **Rotation:** To rotate a password, delete the secret in AWS Secrets Manager and re-run `post-evs-sync-config` (or `deploy-environment`). A new password will be generated and stored.

## Troubleshooting

| Problem | Cause | Fix |
|---------|-------|-----|
| `Key pair does not exist` | Key pair deleted or lost | `aws ec2 create-key-pair --key-name <name>` |
| `ESX version is invalid` | `esxVersion` in config doesn't match region | Set to `null` (auto-resolves) or check `aws evs get-versions` |
| `environmentId` wrong after branch switch | config.json has stale env ID | Update manually or re-run `create-environment` |
| `No EC2 instances found` on post-sync | Hosts deleted or env ID wrong | Verify hosts exist with `list-environment-hosts`; fix env ID |
| `There is already an Environment in VPC` | Previous env not deleted | Delete old env first or reuse it (skip create-environment) |
| Hosts in dirty state after failed bringup | Bringup left vSwitches/vmk adapters | Delete and recreate hosts: `delete-environment-host` → `create-hosts` |
| `HcxNetworkAclId is not accepted` | Switched from public to private HCX | Re-run `pre-evs-sync-config` to clean up stale fields |
| AWS credentials expired during long operation | Session token timeout | Refresh credentials via your credential provider, then retry |

### Rollback

**Linux / macOS:**
```bash
# Delete hosts
for host in esxi01 esxi02 esxi03; do
  aws evs delete-environment-host --environment-id <id> --host-name "$host" --region <region>
done
# Delete EBS volume
aws ec2 detach-volume --volume-id <id> --region <region>
aws ec2 delete-volume --volume-id <id> --region <region>
# Delete environment (also removes VLANs)
aws evs delete-environment --environment-id <id> --region <region>
# Delete secrets
aws secretsmanager list-secrets --filters "Key=name,Values=evs-<env-id>" \
  --query 'SecretList[].Name' --output text --region <region> | xargs -n1 -I{} \
  aws secretsmanager delete-secret --secret-id {} --force-delete-without-recovery --region <region>
```

**Windows (PowerShell):**
```powershell
# Delete hosts
foreach ($host in @("esxi01", "esxi02", "esxi03")) {
  aws evs delete-environment-host --environment-id <id> --host-name $host --region <region>
}
# Delete EBS volume
aws ec2 detach-volume --volume-id <id> --region <region>
aws ec2 delete-volume --volume-id <id> --region <region>
# Delete environment (also removes VLANs)
aws evs delete-environment --environment-id <id> --region <region>
# Delete secrets
(aws secretsmanager list-secrets --filters "Key=name,Values=evs-<env-id>" `
  --query 'SecretList[].Name' --output text --region <region>) -split "`t" | ForEach-Object {
  aws secretsmanager delete-secret --secret-id $_ --force-delete-without-recovery --region <region>
}
```
